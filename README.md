# Sabugo

Open-source root and fiber image analysis, **on the web**. Every established tool in this field — [RhizoVision Explorer](https://github.com/predictivephenomics/RhizoVisionExplorer), WinRhizo™, IJ_Rhizo, Safira — is desktop software: an installer, a specific operating system, in some cases a per-machine licence. Somebody who wants to measure twenty scans has to solve an IT problem first.

Upload the scan, give the DPI, get the numbers: total length, average and maximum diameter, surface area, volume, root tips, branch points, and the four histograms per diameter class. Nothing is stored — image in, numbers out, close the tab and it is over.

## What it does

Both analysis modes are complete and validated: `broken_roots` (washed, disconnected fragments — 26 columns) and `whole_root` (a root system with its topology preserved — 38 columns, adding depth, width, convex hull, solidity, holes and root angles).

The web interface carries the whole thing: upload, the parameter panels, regions of interest drawn on the image, the segmented and skeleton renderings, the metric table with its per-class histograms, and CSV export. Progress arrives over Server-Sent Events while the job runs.

The same pipeline runs from the command line, which is what the validation drives:

```bash
python -m sabugo_worker.cli image.jpg --dpi 600 --threshold 220 --segment --feature
python -m sabugo_worker.cli folder/ --dpi 1200 -o features.csv
python -m sabugo_worker.cli scan.jpg --dpi 600 --roipath rois.csv --prune --smooth
```

Both expose the options of RhizoVision Explorer's three panels:

| Panel | Options |
|---|---|
| Image pre-processing | `--threshold` · `--invert` · `--filter-background-noise` · `--filter-foreground-noise` · `--smooth` + `--smooththreshold` · `--mode` · `--dpi` or `--pixels-per-mm` · `--no-keep-largest` · `--roipath` |
| Feature extraction | `--prune` + `--prunethreshold` · `--dranges` |
| Output display | `--segment` · `--feature` · `--medialwidth` · `--no-medialaxis` · `--no-classcolour` · `--contour` + `--contourwidth` · `--hull` · `--holes` · `--distancemap` |

Plus RVE's *Preview segmented image* as `--preview`, which segments and stops — no skeleton, no metrics, no CSV — and one extra RVE does not have: `--threshold-method otsu`.

## How the numbers were validated

The question is **am I right**, not *do I agree with the reference tool*. Agreement is a weaker question, and no tool dominates it: on simulated roots IJ_Rhizo has better length RMSE than RVE; on copper wires RVE wins volume and IJ_Rhizo wins surface area for a reason that does not generalise. Where the established tools disagree with the truth, and they do, matching them would be the wrong result.

So the measurements are checked against four sources of external truth:

| Ground truth | What it is | What it answers |
|---|---|---|
| **Simulated roots** — [Zenodo 1159845](https://zenodo.org/records/1159845) | 100 root systems generated by the ArchiSimple model (Rose & Lobet, 2018), rendered at 800 and 1200 DPI, with the model's own geometry | realistic, complex geometry — where branching and overlap appear |
| **Copper wires** — [Zenodo 4677546](https://zenodo.org/records/4677546) | 27 scans of calibrated AWG wires, Ø 0.07–2.58 mm, at 600 DPI | *physical* truth: a micrometer for the gauge, trivial topology, so it exercises binarization and calibration and barely touches the skeleton |
| **Synthetic shapes** — generated, no download | a disc stamped along a curve, so the shape's medial axis **is** the curve | truth exact by construction — the only axis that says *which part of the error is which* |
| **The competitors' measurements** — [Zenodo 4677553](https://zenodo.org/records/4677553) | WinRhizo™, IJ_Rhizo and RVE already tabulated, published CC-BY with the RVE paper | nobody has to re-run three tools |

Reported as R², RMSE and MBE, which is the vocabulary the field uses.

**The acceptance criterion was fixed before measuring**: in each metric, Sabugo has to land inside the span the best and the worst of the three established tools already cover between them. It is verifiable and defensible, and it concedes that the three established tools already disagree with each other.

Over the sixteen cells with external ground truth — four metrics × two datasets × two settings each — **Sabugo passes in all sixteen**, on RMSE and on bias, and has the best mean rank of the four:

| Tool | Mean rank | Cells won | Length | Diameter | Surface area | Volume |
|---|---|---|---|---|---|---|
| **Sabugo** | **2.00** | 5 | 2.50 | **1.75** | 2.25 | **1.50** |
| RVE | 2.25 | 4 | **2.00** | 2.25 | 2.25 | 2.50 |
| IJ_Rhizo | 2.50 | **6** | 2.50 | 3.00 | **1.75** | 2.75 |
| WinRhizo | 3.25 | 1 | 3.00 | 3.00 | 3.75 | 3.25 |

IJ_Rhizo wins surface area at both thresholds, and the reason has to be stated: it computes `π·d·l` from a mean diameter, and **a copper wire is exactly a cylinder**. Its model coincides with the object; on a real root system it does not, which is why it places third on the same metric against the simulated roots.

Length is the column Sabugo does worst on, and the deficit turned out not to be its own: the ink in the renderings is 8.5% below the `Σ L·d` the model publishes for the same systems, and the measured error tracks that system by system with correlation +0.85. Discounted, we read slightly long. That analysis, the seven hypotheses measured and refused along the way, and every other number live in [`apps/worker/README.md`](apps/worker/README.md).

### Known limitations

All of these were measured, none is assumed:

- **A global grayscale threshold.** The target is a washed root on a light uniform background, from a flatbed scanner. The RVE paper is explicit that blue paper screens, rhizoboxes and minirhizotrons may not work directly, and neither do they here.
- **Root hairs** inflate practically every measurement. No tool in this comparison treats them, this one included.
- **2D occlusion**, with a number: two roots crossing overstate the volume by 7.6% to 36% per crossing, at every angle. Length only suffers at shallow angles — −5.9% at 15°, zero from 45° on. It is the most serious limitation and it grows with sample density.
- **One-pixel diameter quantization.** The error stays in `[0, +1.5]` px, never negative, with no trend against width. That makes it quantization rather than bias, so a constant subtracted from the radius does not fix it — that was tried, and refuted.
- **An angle at a junction belongs to no single root**: about 4% of frequency leaks into the neighbouring class, up to 1.5° in the mean, on a six-root fan that is close to the worst case.

Sabugo does not classify branching order or separate laterals from axial roots, does not calibrate from a reference object in the image, and stores nothing. The numbers compare treatments within one experiment under identical parameters; they are not absolute measures transferable between studies.

### Running the comparison

```bash
cd apps/worker
.venv/Scripts/python validation/compare.py
.venv/Scripts/python validation/wires.py
.venv/Scripts/python validation/synthetic.py
```

The first two need the Zenodo downloads — [`apps/worker/README.md`](apps/worker/README.md) says which files and where they go. The third renders its own shapes, needs no download, and runs in CI.

Results are versioned in `apps/worker/validation/results/`, and both READMEs render their tables from those CSVs through a test that fails when they drift. A number typed into a README by hand is a number that starts lying on the second run.

## Development

```bash
bun install
bun run dev      # web on :5173, api on :3000
bun run check    # biome + typecheck, what CI runs
bun test
```

`bun run dev` starts the Svelte client and the Hono API together; Vite proxies `/api` to the API, so dev is same-origin like production. The Python worker is separate and has its own environment:

```bash
cd apps/worker && python -m venv .venv && .venv/Scripts/pip install -e ".[dev]"
.venv/Scripts/pytest
```

The two test suites are separate and neither runs the other. Everything about the worker — the algorithm, what was ported and from where, the fixtures and how to run them — is in [`apps/worker/README.md`](apps/worker/README.md).

## Production

One Docker Compose service. No database, no Redis, no volume, no state: `docker compose down -v` loses nothing, because there is nothing to lose. The API serves the client's static build alongside `/api/*`, and the Python worker runs as a subprocess inside the same container, so the image carries both Bun and Python.

```bash
cp .env.example .env    # set the limits, and the port, if the defaults do not fit
bun run compose:up      # docker compose -f infra/docker-compose.yml --env-file .env up -d --build
curl http://localhost:${PORT:-3000}/api/health
```

`apps/api/src/lib/env.ts` validates the configuration at startup and fails naming the variable: a misconfigured container should die at `docker compose up`, not half an hour later on the first upload. Two constraints that are not preference:

- **The runtime image is Debian, not Alpine.** `opencv-contrib-python-headless` publishes no musl wheel, so on Alpine pip falls back to compiling OpenCV from source. Debian's Python is externally managed (PEP 668), so the worker installs into a venv at `/opt/venv` rather than with `--break-system-packages`.
- **Whatever terminates TLS in front of the API has to speak HTTP/2.** Compose publishes the API on `:3000` and nothing else; putting it on a domain is the deployment's job. Every open tab with a running job holds a Server-Sent Events stream, and under HTTP/1.1 browsers cap around six connections per domain — the seventh tab hangs, silently.

Without Compose: `bun run build` produces `apps/web/dist`, and `bun run start` runs the API already serving it.
